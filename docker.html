Docker Mode ​

When you run a coding CLI tool, it has full access to your machine — your files, your terminal, your .env, your SSH keys, everything.

Docker mode puts it in a box. The model can only touch the workspace you mount and nothing else. It can't read your secrets, wreck your system, or do anything outside the container.

All 5 CLI tools (Claude Code, Gemini CLI, Codex CLI, Copilot CLI, OpenCode) work in Docker mode.

When to Use Docker Mode ​

Use Docker mode when:

  • Working on open-source projects — You don't want the model accidentally committing your secrets or reading unrelated files.
  • Running untrusted prompts — If someone sends you a prompt to run, sandbox it first.
  • CI/CD pipelines — Automated runs should always be isolated. No reason to give a pipeline agent access to your whole machine.
  • Team environments — Keep agent execution predictable and reproducible across machines.

For quick personal tasks in your own repo, normal mode is fine. But if there's any doubt, Docker mode is the safe default.

WARNING

Containers still have outbound network access — this is needed for API calls.

Setup ​

Prerequisites ​

  • Docker Desktop or Docker Engine installed and running
  • The docker command available in your terminal

Build the Image ​

Build the Docker image (one-time):

bash
cloding docker build

This creates a container with Node.js and all supported CLI tools pre-installed. The image is cached locally — you only need to rebuild when cloding updates.

Rebuilding

After updating cloding (npm update -g cloding), rebuild the Docker image to get the latest version inside the container:

bash
cloding docker build --no-cache

Usage ​

bash
cloding docker shell                              # Interactive session
cloding docker run "fix the bug"                   # Run a prompt (default: qwen)
cloding docker run -m sonnet-a "review code"       # Direct Anthropic API
cloding docker run -m codex-5 "debug my tests"     # ChatGPT paid plan
cloding docker run -m opus-p "make a plan"         # Claude Max (no key needed)
cloding docker run -w ./myproject "add tests"      # Mount workspace

Your workspace gets mounted read-write at /workspace inside the container. That's the only thing the model can touch.

Auth in Docker ​

Docker mode automatically passes your auth environment variables into the container. The required env var depends on the model you choose:

ModelRequired Env Var
qwen, deepseek, haiku, sonnet, opusOPENROUTER_API_KEY
haiku-a, sonnet-a, opus-aANTHROPIC_API_KEY
gemini-3-aGOOGLE_API_KEY
codex-5-aOPENAI_API_KEY
copilotGITHUB_TOKEN
-p variants, codex-5, gemini-3No key needed (paid plan)
bash
# Examples
export OPENROUTER_API_KEY=sk-or-v1-...
cloding docker run "fix lint errors"

export ANTHROPIC_API_KEY=sk-ant-...
cloding docker run -m sonnet-a "review code"

# No key needed for paid plans
cloding docker run -m opus-p "architecture review"

Volumes and Persistence ​

By default, cloding mounts your current directory (or the path you specify with -w) into the container:

bash
# Mount current directory
cloding docker shell

# Mount a specific project
cloding docker run -w /home/user/projects/my-api "add tests"

What persists: Any changes the model makes to files in the mounted workspace are written directly to your host filesystem. They survive after the container stops.

What doesn't persist: Anything installed or created outside /workspace (npm packages in /usr/lib, temp files in /tmp, etc.) is lost when the container stops.

Installing dependencies

If your project needs npm install or similar, the model can run it inside the container. The node_modules will be created in your mounted workspace and persist. But globally installed tools won't.

Resource Limits ​

Control how much CPU and memory the container can use:

bash
cloding docker run --memory 4g --cpus 2 "refactor the auth module"
FlagDefaultDescription
--memoryNo limitMemory limit (e.g., 2g, 512m)
--cpusNo limitCPU limit (e.g., 1, 0.5, 4)

Setting limits prevents a runaway process from consuming all your system resources.

Container Management ​

bash
cloding docker status    # Show running containers
cloding docker stop      # Stop all containers
cloding docker clean     # Remove stopped containers

Cleanup

Stopped containers take up disk space. Run cloding docker clean periodically, or after long sessions.

Additional Docker Options ​

bash
cloding docker run --name my-container "prompt"    # Custom container name
cloding docker run --no-rm "prompt"                # Keep container after exit

Custom Docker Images ​

If your project needs specific tools or runtimes (Python, Go, Rust, etc.), you can extend the base image:

dockerfile
FROM cloding:latest

# Add Python
RUN apt-get update && apt-get install -y python3 python3-pip

# Add project-specific tools
RUN pip3 install pytest black

# Pre-install project dependencies
COPY requirements.txt /tmp/
RUN pip3 install -r /tmp/requirements.txt

Build your custom image:

bash
docker build -t cloding-python -f Dockerfile.custom .

Security Model ​

Docker mode provides these security boundaries:

  • Non-root user inside the container (UID 1000)
  • No access to host filesystem (except mounted workspace)
  • No access to your SSH keys, .env files, or secrets
  • Resource-limited CPU and memory
  • Network isolation via cloding-net bridge network
  • Outbound network only (for API calls)

What Docker mode does NOT protect against

  • Outbound data exfiltration — The container has network access and could theoretically send data to external servers via API calls.
  • Workspace file destruction — The mounted workspace is read-write, so the model can delete files in it.
  • Prompt injection — If your codebase contains malicious instructions, the model may still follow them inside the container.

Docker mode is a practical safety layer, not a security guarantee.

Troubleshooting ​

docker: command not found ​

Install Docker Desktop or Docker Engine. On Linux, you may also need to add your user to the docker group:

bash
sudo usermod -aG docker $USER
# Log out and back in for the change to take effect

permission denied on workspace files ​

The container runs as a non-root user. If your workspace files have restrictive permissions:

bash
chmod -R u+rw ./my-workspace

Container exits immediately ​

Check the container logs for errors:

bash
docker logs $(docker ps -a -q --filter ancestor=cloding --latest)

Common causes: missing API key, or the mounted workspace path doesn't exist.

Container can't access API ​

Make sure the required API key is set in your current shell before running Docker commands:

bash
echo $OPENROUTER_API_KEY    # Should not be empty
