Examples ​

Real-world workflows showing cloding in action. Each example includes the command, what it does, and tips for getting the best results.

Build an API Endpoint ​

Add a new REST endpoint to an Express API with validation, error handling, and tests.

bash
cloding -p "Add a POST /api/users endpoint to src/routes/users.ts that:
- Accepts { name, email, role } in the body
- Validates all fields (email format, role must be 'admin' or 'user')
- Returns 201 with the created user on success
- Returns 400 with validation errors on failure
- Add tests in tests/routes/users.test.ts"

Why this works well

The prompt is specific about the endpoint path, request shape, validation rules, response codes, and test file location. The more context you give, the better the output.

Debug an Issue ​

Track down and fix a bug using the agent's ability to read files, run tests, and trace the problem.

bash
cloding -p "The search endpoint at /api/search returns 500 when the query parameter
is empty. Investigate the issue in src/routes/search.ts and related files, find the
root cause, fix it, and add a test case for empty queries."

Tip: Reference the specific file and error. The agent will read the file, trace the logic, identify the bug, and write both the fix and a regression test.

Refactor with a Powerful Model ​

Use a powerful model for refactoring to get better architectural decisions.

bash
cloding -m sonnet-a -p "Refactor src/services/auth.ts to use the middleware pattern:
- Extract token validation into a middleware function
- Extract role checking into a separate middleware
- Update all routes in src/routes/ that use auth to use the new middleware
- Keep all existing tests passing"

Tip: Use sonnet or opus for refactoring — they handle multi-file changes and architectural patterns better than cheaper models.

Add Tests to Existing Code ​

Generate comprehensive tests for an existing module.

bash
cloding -p "Add unit tests for src/utils/validation.ts. Cover:
- All exported functions
- Edge cases (empty strings, null, undefined, special characters)
- Error cases (invalid inputs that should throw)
- Put tests in tests/utils/validation.test.ts
- Use Jest with describe/it blocks"

Tip: Specify the test framework and structure you want. The agent will read the source file, understand the functions, and generate meaningful tests.

Code Review with Different Tools ​

Use different tools for reviewing code:

bash
# Review with Claude Opus via paid plan
cloding -m opus-p -p "Review all files in src/api/ for:
- Security vulnerabilities (SQL injection, XSS, auth bypass)
- Performance issues (N+1 queries, missing indexes)
- Error handling gaps (unhandled promises, missing try/catch)
Write findings to REVIEW.md with severity levels and suggested fixes."

# Review with Codex
cloding -m codex-5 -p "Review the last 5 commits for bugs and style issues"

# Review with Gemini (large context window)
cloding -m gemini-3 -p "Review the entire src/ directory for consistency issues"

Tip: Different tools have different strengths for reviews. Opus excels at deep analysis, Gemini handles large codebases well.

Multi-Model Workflow ​

Use different models for different stages of the same task — plan with Opus, implement with Qwen.

bash
# Step 1: Plan the architecture with Opus (via paid plan)
cloding -m opus-p -p "Analyze the codebase and create a detailed plan for adding
WebSocket support to the chat module. Write the plan to PLAN.md with:
- Files to create/modify
- Data flow diagram
- Message format specification
- Error handling strategy"

# Step 2: Implement with Qwen (cheap, fast)
cloding -p "Implement the WebSocket chat feature following the plan in PLAN.md.
Create all necessary files and modify existing ones as specified."

# Step 3: Review with Sonnet (via direct API)
cloding -m sonnet-a -p "Review the WebSocket implementation against PLAN.md.
Check for missed requirements, bugs, and edge cases. Fix any issues you find."

Tip: This three-step workflow costs a fraction of doing everything with Opus, and the quality is comparable because the expensive model only handles the hard part (planning).

Multi-Tool Examples ​

Use different CLI tools for different tasks:

bash
# Use Copilot for GitHub-specific tasks
cloding -m copilot -p "help me fix the CI pipeline"

# Use Codex for debugging
cloding -m codex-5 -p "debug why my tests are failing"

# Use Gemini for analyzing large files
cloding -m gemini-3 -p "analyze this 5000-line file and suggest refactoring"

Pipeline Example ​

Use pipeline mode for automated multi-stage workflows.

bash
# Standard pipeline: Plan -> Explore -> Code -> Review
cloding pipeline "Add rate limiting to all API endpoints" --workspace ./myapp --no-docker

# Fan-out: Plan once, code in parallel, review together
cloding pipeline -c configs/qwen-fanout.yaml "Add input validation to all form components"

# Human-in-the-loop: Approve each stage before proceeding
cloding pipeline -c configs/human-loop.yaml "Migrate from REST to GraphQL"

Tip: Start with --no-docker for faster iteration. Add Docker for CI runs or when working on sensitive projects.

CI/CD Integration ​

Automate code quality tasks in your CI pipeline.

bash
# In your CI workflow (e.g., GitHub Actions)

# Auto-fix linting issues
cloding -p "Fix all ESLint errors and warnings in the codebase"

# Generate missing tests
cloding -p "Find functions in src/ without corresponding tests and add them"

# Review PR changes with direct API
cloding -m sonnet-a -p "Review the changes in the last commit for bugs and style issues.
Write findings to review-output.md"

Tip: Use qwen for high-volume CI tasks to keep costs low. Set OPENROUTER_API_KEY as a repository secret.

Docker Sandboxed Session ​

Run the agent in an isolated container for security.

bash
# Build the image (one-time)
cloding docker build

# Interactive sandboxed session
cloding docker shell

# Run a sandboxed prompt on a specific project
cloding docker run -w ./open-source-project "add comprehensive error handling"

# Use different tools in Docker
cloding docker run -m sonnet-a "review code for security issues"
cloding docker run -m codex-5 "debug my failing tests"
cloding docker run -m opus-p "architecture review"

# Resource-limited execution
cloding docker run --memory 2g --cpus 1 "refactor the database module"

Tip: Always use Docker mode when working on open-source projects or running prompts from untrusted sources.

Tips for All Examples ​

  • Be specific — Include file paths, function names, and expected behavior
  • State constraints — "Don't install new packages" or "Keep existing tests passing"
  • Reference files — "See the pattern in src/services/users.ts" helps the agent match your codebase style
  • Break complex tasks — Multiple focused prompts beat one giant prompt
  • Check the output — Always review changes before committing, especially with cheaper models
  • Mix models — Use expensive models for planning and review, cheap models for implementation
