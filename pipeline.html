Pipeline Mode ​

Pipeline mode runs multi-stage coding workflows with parallel fan-out. Assign different models to different stages — Opus for planning, Qwen for coding.

┌─────────┐    ┌───────────┐    ┌─────────────────────┐    ┌──────────┐
│  PLAN   │───▶│  EXPLORE  │───▶│       CODE          │───▶│  REVIEW  │
│ (opus)  │    │  (sonnet) │    │  ┌─────┐ ┌─────┐   │    │ (sonnet) │
│         │    │           │    │  │agent│ │agent│   │    │          │
│         │    │           │    │  │  1  │ │  2  │   │    │          │
│         │    │           │    │  └─────┘ └─────┘   │    │          │
└─────────┘    └───────────┘    └─────────────────────┘    └──────────┘

Each stage's output feeds into the next. The Code stage can fan out to multiple parallel agents, each working on a different part of the task.

Setup ​

Pipeline mode requires Python 3.11+:

bash
cd pipeline && pip install -e .

TIP

Pipeline mode is optional. You can use cloding without it — pipelines are for complex, multi-step workflows where you want fine-grained control over model allocation.

Usage ​

bash
cloding pipeline "Add authentication" --workspace ./myapp --no-docker

With a specific config:

bash
cloding pipeline -c configs/qwen-fanout.yaml "Refactor the DB layer"

With Docker isolation:

bash
cloding pipeline "Add tests for the API" --workspace ./myapp

Pipeline Stages ​

A typical pipeline runs through these stages:

1. Plan ​

Analyze the task and create a development plan. Use a powerful model here — the plan guides everything downstream.

  • Recommended model: opus or sonnet
  • Output: A structured plan with file changes, dependencies, and order of operations

2. Explore ​

Examine the codebase to understand the current state. The model reads files, traces imports, and maps the architecture.

  • Recommended model: sonnet or haiku
  • Output: Codebase context that informs the coding stage

3. Code ​

Implement the changes. This is where most tokens are spent, so use a cost-effective model. With fan-out, multiple agents work in parallel on different subtasks.

  • Recommended model: qwen or deepseek
  • Output: Modified files with the implementation

4. Review ​

Review the changes for correctness, bugs, and style. A second pair of eyes catches what the coding model missed.

  • Recommended model: sonnet or opus
  • Output: Review comments, suggested fixes, approval/rejection

Parallel Fan-Out ​

The Code stage can spawn multiple agents that work simultaneously. This is powerful for tasks that decompose naturally:

yaml
stages:
  - name: plan
    model: opus
    prompt: "Break this task into independent subtasks: {task}"
  - name: code
    model: qwen
    parallel: 4
    prompt: "Implement subtask: {subtask}"
  - name: review
    model: sonnet
    prompt: "Review all changes for consistency: {code}"

With parallel: 4, four Qwen agents run concurrently. Each gets a subtask from the Plan stage's output. The Review stage then sees all changes together.

When fan-out helps:

  • Adding tests across multiple modules
  • Refactoring several files with the same pattern
  • Implementing multiple API endpoints
  • Migrating code patterns (e.g., callbacks to async/await)

When it doesn't:

  • Tightly coupled changes where order matters
  • Single-file tasks
  • Tasks that require sequential reasoning

Human-in-the-Loop ​

The human-in-the-loop config pauses between stages and asks for your approval before continuing:

bash
cloding pipeline -c configs/human-in-the-loop.yaml "Redesign the auth system"

The pipeline will:

  1. Plan the changes and show you the plan
  2. Wait for you to approve, modify, or reject
  3. Code the approved plan
  4. Wait for you to review the code
  5. Review and finalize

This is ideal for high-stakes changes where you want to stay in control.

Custom Pipelines ​

Create a YAML config to define your own pipeline:

yaml
name: my-pipeline
description: Custom pipeline for API development

stages:
  - name: plan
    model: opus
    prompt: "Analyze and plan: {task}"

  - name: code
    model: qwen
    parallel: 3
    prompt: "Implement: {plan}"

  - name: review
    model: sonnet
    prompt: "Review these changes: {code}"

Place your config in the pipeline/configs/ directory and reference it with -c.

Config Reference ​

FieldRequiredDescription
nameYesPipeline name
descriptionNoHuman-readable description
stagesYesArray of stage definitions
stages[].nameYesStage name (used in output)
stages[].modelYesModel shortcut or OpenRouter ID
stages[].promptYesPrompt template ({task}, {plan}, {code} are replaced)
stages[].parallelNoNumber of parallel agents (default: 1)
stages[].approveNoPause for human approval before this stage

Tips ​

  • Start with quick for simple tasks, upgrade to default or fan-out for complex ones.
  • Fan-out works best when the Plan stage produces clearly separated subtasks.
  • Monitor costs — pipelines use multiple models across multiple stages. A complex pipeline with Opus planning can cost more than a single Qwen session.
  • Use --no-docker for faster iteration during development. Add Docker back for production/CI runs.
